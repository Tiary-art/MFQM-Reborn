# MFQM Reborn — 工程重整 R0：原版全量解构、复原覆盖审计、AI 近似逻辑清理基线

> **交给 Codex 的正式任务书｜优先级 P0｜目标平台 Minecraft 1.20.1 / Forge 47.2.0 / Java 17**
> **本轮名称：Reconstruction Program / R0（工程重整基线）**
> 此任务启动一个长期、可核查、可继续推进的“原版证据 → 新旧差异 → 有证据的替换与清理 → 验证 → 复原覆盖更新”流程。**不是再做一份泛泛的研究报告，也不是立即把现有工程推倒重写。**

## 0. 用户意图：必须优先满足

用户要忠实复原 **More Fun Quicksand Mod (MFQM) 1.1.1 / Minecraft 1.7.10** 在 **MFQM Reborn / Minecraft 1.20.1** 的全部可确认内容，包括但不限于：方块、独立物品、旧 metadata 变体、名称、创造栏、实体、流体、资源、动态渲染、GUI、污渍、动作与下沉、世界生成、结构、配置、事件、网络和各种交互。

用户已在 Windows 上实测 Phase 9 私有材质 JAR：**仍有紫黑缺失贴图、材质不正确/不完整、项目内容数量和名称与原版不一致、机制存在明显偏差**。因此不得继续将“导入 PNG 成功”“现有 49 个方块”“测试通过”描述为完整复原。

用户要求：

1. **从头到尾系统分析原版 JAR 的全部内容**，按每个分析对象留有永久档案：原始证据、原文/反编译表达、具体用途、调用关系、关键条件、现代对应、仍未知部分。
2. **完整盘点新版工程**，建立原版对象与新版对象的双向对应；逐一揭示未注册、缺失、近似、错误或多余的实现。
3. **审计早期 AI 生成的近似代码与重复逻辑**。如果原版已具备更准确的算法，依据证据进行替换，并在验证不回退后删除旧实现，避免让互相冲突的算法长期共存。
4. 把已经查明的原版内容逐步纳入 1.20.1 工程；即使某些玩法暂未实现，原版可见条目也应有可验证的注册/安全占位规划，**但不得靠猜测凑数、伪造原版行为**。
5. 建立以后所有开发阶段都必须更新的**唯一事实来源、差异矩阵、删除决策记录、自动验收门槛**。重视最终质量、模组兼容、既有存档安全，不用短期速度换取更多技术债。

当前主要精力在技术解构与差异审计，不安排材质重绘。原始资源可作为私人分析输入；不要把用户自备原版 JAR/私有材质混进公开构建。

## 2. 总体开发原则（必须写入仓库治理文档）

- **原版为行为证据，现代 Forge 为工程实现边界**：复原语义与可观察效果，不机械复制已过时的 API、线程模型或会损坏现代游戏的实现。
- **每条结论可溯源**：区分 `BYTECODE_CONFIRMED`、`DECOMPILED_INTERPRETATION`、`DYNAMIC_ORACLE_CONFIRMED`、`RESEARCH_ONLY`、`INFERRED`、`UNKNOWN`。反编译文本不能冒充原作者源代码；推测不能写成事实。
- **每一个原版对象必须有状态**，不能丢弃未知或未到达的方法来提高“完成率”。每个新版关键逻辑也必须可反查至原版对象，或标为 `MODERN_BRIDGE` / `SAFETY_COMPAT` / `DEV_TEST` 等有理由的现代必要功能。
- **禁止“先删后补”**：删除/替换物理、注册、网络、存档、资源引用前，给出旧/新行为差异、依赖图和回归证据；高风险重写应分 PR、分提交，可独立回滚。
- **不按代码生成者判断对错**：AI 写的代码可能合理，原版实现也未必能直接在现代版本安全使用。审计对象是证据、行为差异、重复副作用、维护成本和兼容影响。
- **完整注册与完整还原分开计量**：`REGISTERED`、`VISIBLE`、`ASSET_MATCHED`、`BEHAVIOR_PARITY`、`MULTIPLAYER_VALIDATED` 分别验收；不能用一个 PASS 掩盖未完成。
- **零默认开启未经验证的危险机制**：实验性自然生成、全局移动替换、存档迁移等要有开关与回滚措施；正式已验证机制不得因改制而无故变成默认关闭。
- **无虚构交付**：报告、截图、测试向量、Git 提交、安装 JAR、原版运行结果都必须有真实证据；不能用开发类路径测试代替正式客户端安装 JAR 测试。

## 4. R0-A：原版 JAR 与现代工程的双向全量清单

### 4.1 原版输入与字节级盘点

在私人工作环境只读打开原版 JAR，记录 SHA-256、ZIP 内路径、大小、CRC、类型、各资源 SHA-256、类路径、内部类与匿名类，避免 zip 路径碰撞、大小写碰撞、缺条目、重复条目。建议为每个文件生成稳定 `original_file_id`，为每个类生成 `class_id`，为每个字段/方法生成包含 **JVM descriptor** 的 `member_id`：方法重载不能被简单名称覆盖。

逐一登记全部文件，分类 `CLASS / PNG / ANIMATION / SOUND / LANGUAGE / METADATA / OTHER`，以及 `RELEVANT / POSSIBLY_UNUSED / UNREACHABLE_PROVEN / UNRESOLVED`。**`UNREACHABLE` 必须有引用/反射/事件/注册入口审查证据，不可因为搜索不到调用者就断言死代码。**

每个原版类至少提取：super、interfaces、完整字段签名、全部方法签名、可用注解、常量池重要引用、方法调用/字段读写、注册和资源引用；记录提取工具、版本、输入 hash。整包计数必须由脚本从原始输入生成，不手填。

对方法库建立至少“名字/descriptor/访问修饰符/代码长度/字节码证据/调用关系/深度分析状态”。以历史研究提供的 **约 1,955 个方法**作为需重新核验的参考值而非硬编码的真值。未能读取方法体的条目明确报错和原因。

### 4.2 不止 Java 的功能清点

从 **真正的旧版注册入口、ItemBlock/Item、metadata、创造栏及资源**抽取：

- 独立 Block、Item、Fluid、ItemBlock、Bucket、Entity、TileEntity、Potion/Effect、Command、CreativeTab 等真实存在的种类（没有证据的种类记 N/A）；
- 每个旧注册名/字段名、metadata/损伤值、可获得性、创造栏可见性、原版显示名称/多语言、贴图与动画、掉落/配方、默认/隐藏/调试状态；
- Event handler、世界生成入口/群系或结构、tick/碰撞、客户端渲染、粒子、HUD/污渍/相机、网络和数据保存；
- 反射、约定名称、条件初始化、可选依赖、外部配置、仅客户端/仅服务器路径、历史未使用路径。

**单位不能混淆**：注册表条目数量、旧 metadata 变体数量、创造栏可见数量、资源文件数量和 Java 类数量分别有自己的分母；不能把 `49 blocks` 当作 `49 items` 或“全部内容”。

### 4.3 现代项目基线盘点

在 `forge-1.20.1/` 建立所有实际注册对象（不是仅扫描 JSON）、全部 Java 类/字段/方法、blockstate/model/texture/item model/lang/loot/recipe/tag/sounds/animations、配置、网络、Mixin（若有）、世界生成入口、GameTest/JUnit、开发/测试开关、存档序列化与兼容层清单。

区分 **公开源代码/公开无原始素材 JAR** 与 **用户本地私人材质 JAR**；不能因为公开版本 `assets/mfqm/textures/*.png` 为 0，就把原版私有资源导入功能当成完全缺失；同时绝不能因为私人 JAR 有 PNG 就把模型、贴图使用者或渲染效果标记为 PASS。

记录所有已存在世界可能保存的 registry ID、block state、block entity 数据、玩家能力/属性、维度/结构数据、mod 配置键和网络包 ID，形成**兼容性冻结清单**。

## 5. R0-B：真正可用于移植的原版分析报告体系

### 5.1 每个原版类必须有独立档案

在 `docs/reconstruction/original/classes/` 下按 JVM 全限定类名生成一类一档（Markdown）及对应机器可读 JSONL/CSV 索引。即使尚未深度分析，也必须列明字段/方法目录、已知角色、已有报告链接、待证问题、分析状态，**不能用同一个泛泛段落代替 161 个类的逐项记录**。对于很短/无业务逻辑的编译器合成类，允许精简，但须列出依据和宿主关联。

每个深度报告固定包含：

1. **身份与原版来源**：稳定 ID、类名/JVM descriptor、原版 JAR SHA、字节码文件路径/哈希、工具版本；本类是客户端/服务端/公共还是不确定。
2. **原文证据（与解释分栏）**：关键方法反编译表达/字节码的精准位置、原始常量及调用顺序；反编译内容注明 `DECOMPILED (not original source)`；提供证据文件链接与行/偏移，报告可用必要短摘录，不需在所有报告机械粘贴庞大重复代码。
3. **它实际上负责什么**：用中文描述可观察行为、触发条件、调用者、调用对象、读写状态、失败/提前返回路径；不确定的地方标 `HYPOTHESIS`。
4. **功能与资源映射**：旧注册、metadata、方块/物品/实体、纹理/图标/声音/渲染、事件入口、配置、生成器等。
5. **行为规范**：输入、输出、副作用、实体/方块状态更新、tick 顺序、随机数调用顺序、旧世界/维度约束、异常及边界。
6. **现代差异**：对应新版文件/方法、现状、是否仅注册/仅资源/仅近似、现代 API 适配、兼容风险。
7. **测试设计**：原版可执行 oracle、固定向量、图像对照或真实游戏测试；未运行的写 `NOT_RUN`。
8. **结论、证据强度、未解问题及下一步**：不允许把未证明的“应该是”写成 `CONFIRMED`。

### 5.2 方法与调用链不能只停留在类级

建立机器可读 `ORIGINAL_METHOD_INDEX`、`ORIGINAL_FIELD_INDEX` 与 `CALL_GRAPH`。对于**每个方法**，至少有一个独立索引记录；对于重要方法，另设深度报告或在该类文档有带锚点的完整方法小节。重要方法判定依据：可产生游戏副作用、参与注册/渲染/生成/网络/状态变化、被跨模块调用、曾出现偏差/风险；不能单纯按代码行数排序。

必须交叉核对：

- 原版调用顺序与现代事件顺序（包含多次 `entityInside`、Tick 边界、客户端/服务端）；
- 实体玩家、非玩家实体、流体、多方块接触、Y 轴速度、属性修改、状态释放、FOV/视角、污渍同步；
- 世界生成的 RNG 种子、消费顺序、写块 flags、跨区块与掉落/邻块副作用；
- metadata/图标选择、ItemBlock 名称与物品图标、动态渲染、粒子及透明面。

### 5.3 R0 首批重点深度档案（必须实际完成，不能只建空文件）

至少完成下列**模块的证据链与现代对照**，允许拆为多份档案而不是每项只有一页：

- 原版注册总入口与所有注册分派：**方块/独立物品/旧变体/创造栏/语言/资源**（先解决数量和名称争议）；

- `Stuck` 属性/租约与现有 B1/B2 垂直运动、防抖动保护的关系；
- 原版材质选择与旧 metadata、流体 still/flow、特殊模型，针对已出现的紫黑缺失纹理建立可追溯案例；
- 原版污渍状态与视觉层、清洗、客户端资源使用入口；
- 现有自定义世界生成的原版入口与新版现状（只审计、不默认激活）。

对无法证实原版类名、方法签名或路径的项目，使用查找流程而非编造；所有宣称“首批已完成”项目必须满足 §12 的证据门槛。**复用 Phase 1–5 原始字节码和实测向量，不重复从头研究已经证实的数学事实；对于历史报告错误或证据缺失，再定向重测。**

## 6. R0-C：原版与 1.20.1 工程的双向复原矩阵

建立唯一的 **Restoration Coverage Matrix**，同时支持从原版查新版、从新版反查原版。

### 6.1 逐项核对的最小粒度

- 原版对象：`CLASS / METHOD / FIELD / BLOCK / ITEM / ITEMBLOCK_VARIANT / FLUID / ENTITY / RENDERER / MODEL / TEXTURE / ANIMATION / SOUND / GUI / CONFIG / COMMAND / WORLDGEN / STRUCTURE / FEATURE / NETWORK / SAVE_DATA / BEHAVIOR_CASE / OTHER`；
- 对每个对象，分别标记 **是否存在现代映射、现代代码位置、是否注册、是否可见、资源是否字节/绑定正确、名称是否正确、实际行为与原版是否一致、测试级别、兼容风险、最后验证日期**；
- `MISSING`、`UNREGISTERED`、`PLACEHOLDER`、`APPROXIMATION`、`MISMATCH`、`PARTIAL`、`MATCHED_VERIFIED`、`NOT_APPLICABLE_PROVEN`、`UNKNOWN`、`BLOCKED` 等状态含义必须在 README 固定，不能随意混用；
- 一个旧注册内容可映射多个现代 ID（metadata 拆分）；多个原版实现可共用一个现代适配器，但须保留**各自原版差异**和单独测试；映射表应为多对多，不能简单强制一对一；
- 所有现代游戏逻辑没有原版对应时，必须说明 `MODERN_BRIDGE`、`COMPATIBILITY_SAFETY`、`DEV_ONLY`、`UNJUSTIFIED` 或 `UNKNOWN`，避免“AI 自创功能”藏在共享父类里。

### 6.2 分开统计覆盖率

输出具备**可核查分母**的多项数字：

- 原版文件索引覆盖率、类索引覆盖率、方法索引覆盖率、**深度行为分析覆盖率**；
- 注册对象与 metadata 变体识别率、现代注册率、创造栏正确显示率；
- 原版纹理/模型/图标/动画引用确认率、私人 JAR 资源打包率、**游戏内视觉验收率**；
- 原版行为案例总数、原版 oracle 覆盖率、现代行为等价通过率；
- 待清理近似实现总数、经验证替换总数、已安全删除总数；
- 客户端、专服、存档、联机/整合包的真实测试覆盖率。

覆盖率报告必须同时列出 `N_total`、`N_verified`、`N_partial`、`N_unknown`、`N_blocked`、`N_not_run`、`N_not_applicable_with_proof`；**未知/阻塞不得偷偷从总数分母中排除**，生成百分比的脚本和数据都必须入库。

### 6.3 明确用户反馈与测试反馈入口

建立 `USER_OBSERVED_GAPS`，把用户游戏截图中的“紫黑模型、名称未还原、数量不足、占位纹理、物理差异”分别设为可关闭的 issue；需提供最新 JAR 的 ID/hash、复现步骤、坐标/方块 ID 或物品 ID、预期原版依据、结果截图/日志、责任模块。**不能只写“用户感觉不对”而不给排查路径。**

## 7. AI 近似代码、重复实现和技术债的专项审计

本轮必须遍历**全部现代 Java 源文件与主要资源配置**，并检查 Git 历史/Phase 旧报告，输出完整清理候选台账；不要求原代码是 AI 编写才可审计，也不因为“AI”字样就一律删除。

优先审计但不限于：

1. `LegacyBlocks` 通用分类、`MaterialProfile` 及早期三类下沉近似；材料共享逻辑是否遗漏原版不同元数据、随机和状态机；
2. `CoreSinkingBlock`/其他碰撞处理、B1/B2 的 Y 轴防抖动、StuckLease、StuckAdapter、OriginalContactBridge 是否有重复限制/双重应用/失效后遗留属性；
3. 污渍层与清洗是否是全身瞬时覆盖、统一计时器或错误的客户端算法；
4. 旧 metadata/颜色/物品名/模型资源配置中的人工猜测；
5. 世界生成模拟/测试适配与真实游戏生成入口的混淆；
6. 流体、方块材质、不真实物品图标、粒子、音效、相机/FOV 的近似/重复路径；
7. 旧阶段测试命令、实验开关、DEBUG_ONLY 模块和生产代码互相依赖；
8. 资源文件/注册条目/数据包中失效或错连的路径、重复功能、无引用对象；
9. 兼容层与既有存档/网络数据依赖、可能被错误清理的现代安全逻辑。

每条候选按下列类别裁决：

- `KEEP_EXACT_OR_NECESSARY`：原版一致或现代适配必需；
- `KEEP_TEMPORARILY`：虽近似但暂无经过验证的替代，不能直接删除；
- `REPLACE_FROM_ORIGINAL`：有明确原版证据与现代替代方案；
- `MERGE_DUPLICATE`：重复责任与副作用可以证明并合并；
- `DELETE_AFTER_PARITY`：存在替代且已证明没有调用/保存兼容风险；
- `REMOVE_DEV_ONLY`：仅测试用并在生产中多余，保留必要诊断入口/测试；
- `BLOCKED_EVIDENCE`：需进一步证明，不准武断。

**每项必须附：** 旧路径/类/方法/范围、新版消费者、原版对应证据、行为差异/为何非原版、依赖与副作用、替代方案、测试与回滚、决策/状态、责任/PR。能精确指出既有错误且有测试证据的，按风险排序优先排入未来修复阶段。

## 8. “替换原版代码后删除旧代码”的强制安全门槛

对于删除或覆盖任何运行时实现，必须全部满足：

1. **原始证据明确**：原版字节码/反编译位置、输入/输出/副作用与重要分支，注明动态验证边界。
2. **现代替代逻辑可运行**：不能直接把 1.7.10 的 Java/API 硬贴到 Forge 1.20.1；客户端渲染、专服、事件、注册和数据保存依现代规则适配。
3. **对比验证**：同输入下行为向量或事件轨迹与原版一致；无法用老游戏验证的部分须标不确定，并保留可撤销开关。
4. **保留已验证安全修复**：尤其 B1 的 Y 抖动/落地音/入沙稳态、服务器权威运动、安全脱离、属性清理、低 TPS/跨区块限制，不能因追求原版调用结构而倒退。
5. **无双重执行**：证明旧、新路径不会同时对相同玩家/实体施加两次减速、碰撞处理、伤害、网络包、资源渲染或 tick 修改。
6. **存档/兼容影响明确**：现有 `mfqm:` 注册 ID、BlockState、数据键、配方、配置、网络格式不可随意更名或删除；需要迁移则先提供实测迁移/回滚测试。
7. **可回滚与可审计**：每一批改动单独提交，旧版本对照构建可用，附代码 diff、测试日志、删除/替代清单。
8. **独立验收结果**：原版一致性 PASS、现代兼容 PASS、用户体验测试状态彼此独立；后者 NOT_RUN 不得冒充 PASS。

本轮 **R0-E** 仅允许在上述全部满足时完成**一个小规模的安全示范修复**；否则**只产出分类与后续任务清单是正确行为**，不视为失败。绝不能为了减少代码行数先破坏玩法。

## 10. 编写、证据、数据治理与工具质量

- **复用而不重做**：逐项建立对 `research/task-001`、`original-mechanics-phase1`、`original-phase2..5`、`docs/phase6..9`、Phase 9 原版纹理映射、现有 JUnit/GameTest 的引用；历史报告有冲突时保留不同来源、证据等级与待测项，不静默覆盖原结论。
- **确定性脚本**：同一输入多次运行得到同一稳定 ID 和相同排序/哈希；有明确 `--input-jar`、`--repo-root`、`--out-dir`、`--verify` 或等价参数；无输入时给明确错误/部分模式，禁止制造虚假的空成功结果。
- **Windows 支持**：CSV/JSON/MD 显式 UTF-8；Windows `subprocess` 的 `.bat` 启动使用实测的 `cmd.exe /c gradlew.bat` 或等价可靠方式，支持空格、中文、方括号路径；不要重复 Phase 9 的 `cp932` 和 Gradle `WinError 2`。不能在 Linux 测过后声称 Windows 通过。
- **来源证据不可伪造**：对反编译/字节码提供原始类与 JVM descriptor、关键偏移/行、原始 hash、工具链；“原文”=有出处的反编译或字节码，不等于原作者编辑时的源码。原版代码的自动生成伪代码与原始证据分栏。
- **测试真实输出**：基线 PASS 与后续 PASS 不混淆；保留故障日志、被跳过的测试、not run 的原因；检测 JUnit XML 与 GameTest 原始报告，不单凭 Gradle `BUILD SUCCESSFUL`。
- **证据一致性**：所有 CSV 外键可解析、报告所指文件存在、引用路径大小写一致、目标 Forge 源码路径存在；失败时自动生成 orphan/invalid-report 而不是忽略。
- **数据来源边界**：原始 JAR/用户私有 PNG/私人构建仅在本地分析使用；公开 PR 交付结构化分析、来源索引、必要的最小证据与代码工具，不要求将原始私有 JAR 或私有资源直接提交。把版权和材质重绘作为非本轮技术主题，不以此拖延分析工作。

## 12. 验证、交付与验收标准

### 12.1 必须运行/记录的验证

- R0 原版输入若可用：完整 ZIP 枚举与 `.class`/资源文件总数闭环；每类有档案或标注状态；每方法/字段有索引；所有原版文件都有机器可查去向；与历史 161 类/300 资源等基线交叉验证差异。

- 所有结构化主表键唯一、外键有效、路径实际存在或 `MISSING` 明确标记、每个索引项有状态、统计脚本结果与报告数值完全一致。
- 现代全部源码/配置/资源清单完成（含未映射对象），已有注册/命名/模型缺陷进入清单，且能生成 `orphan`/`unmapped`/`unverified` 报告。
- 每个重点档案必须附最少一个原版证据定位、现代对应差异、具体行为说明和相应验证计划；若可执行测试，则提供实际运行向量/日志。
- 新版工程执行 `clean test build` 与可用的 GameTests；尽量跑专服启动/退出；若本轮不涉及玩法修改也要留下基线日志。Windows、正式启动器、多人真实体验没有实测就写 `NOT_RUN`。
- 若 R0-E 有修改：新增原版对照测试并对每一项被删除/替换代码证明无重复执行、无存档破坏、无 B1/B2 回归；失败则回退本次修改但保留审计信息。
- 交付清单、源代码 Git commit、JAR（若作为本轮产物）及 SHA256、测试结果必须彼此对应；缺少 JAR 时明确是否是有意只交付分析工具，不能假装已打包。

2. **原版文件/类/方法/字段/注册/资源的结构化主索引**，附原版输入验证状态、稳定 ID、缺口列表。
3. **所有原版类的索引与档案状态**，以及 §5.3 中重点模块的充分深度分析报告；没有做完的明确 `NOT_ANALYZED` 或 `PARTIAL`。
4. **当前 1.20.1 全量盘点**和**原版→现代、现代→原版双向差异矩阵**，附真实覆盖率统计与口径。
5. **AI 近似逻辑与重复代码的全工程审计台账**、分批替换/删除计划、保留哪些现代适配的理由。

### 12.3 PASS / PARTIAL / BLOCKED 规则

- **R0-A PASS**：能够证明每一原始条目已索引；独立输入 SHA 校验、完整性工具通过。若 JAR 不可得仅可 `PARTIAL`/`BLOCKED`。
- **R0-B PASS（限“索引完成 + 首批深度分析”）**：161 类或实际输入全部类各有档案/状态，所有方法与字段有可查目录，§5.3 重点对象各自有深度证据分析；**不得宣传“全 161 类每个方法都已彻底分析”**，除非确有实证。
- **R0-C PASS**：当前工程所有逻辑与资源都有索引，所有可识别原版对象有现代映射或显式缺口，清理候选不漏掉现代无原版对应实现；差异可双向查询。
- **R0-D PASS**：索引/外键/覆盖率校验工具真实运行通过，现有构建与已覆盖测试未回退，提交与证据可复核。
- **R0 整体 PASS** 仅表示“**重整基础设施及本轮约定审计范围已建立**”，**绝不意味着 MFQM Reborn 内容或玩法已经完整复原**。
- 任一验证缺失、输入不可得、只生成空档案、报告数字无法追溯、测试 NOT_RUN 误标为 PASS、或强行删除未经验证的代码：整体 `PARTIAL` 或 `BLOCKED`，列出真实缺口。

## 13. 给 Codex 的执行顺序和禁止事项（必须遵守）

**现在就执行：**

1. 确认当前 HEAD、当前分支、原版输入有无、原版 SHA、现有研究文件的可访问范围；创建独立 `reconstruction-r0` 分支/草稿 PR（依其环境权限），先冻结基线并记录风险。
2. 调用既有研究索引，不重复无意义的解码；生成原版完整文件/类/成员表与新版全量清单；给出确定性脚本和可机检格式。
3. 产出类档案索引及重点的深度原文/字节码证据报告；把旧注册、metadata、资源与新注册/模型/语言绑定起来。
4. 完成全项目新旧覆盖矩阵、代码清理候选与实际缺口优先级；重点显示**原版有而新版没有**、**新版有但原版无对应**、**新版实现仍为近似**三大类。
5. 跑数据校验、基础构建与回归，形成后续可直接执行的 R1/R2 等 work packages；将全部新表格/工具/报告/日志提交，可供用户下载合并项目 ZIP 检查。
6. **本轮不启动大规模玩法重构**；只有证据齐全、测试可覆盖、可回滚的极小修复才可在独立提交进行。

**禁止：**

- 为了追求覆盖率，凭直觉补注册 ID、旧 metadata、纹理名、原版算法或原始源码。
- 混淆“原版编译字节码”“反编译表达”“Codex 自己写的等价伪代码”。
- 因为旧代码看似 AI 生成就直接删除，或把多个原版差异明显的材料继续合成一个通用行为并标记 `MATCHED_VERIFIED`。
- 遗漏旧版独立物品与 ItemBlock 变体，只统计旧方块数量；把未到达/反射触发路径武断判死代码。
- 用历史 SHA 审计、纯 Java 数学测试、开发客户端资源路径代替实际现代游戏运行与原版行为验收。
- 为了方便开发改掉既有 `mfqm:` 注册 ID、清理掉稳定性修复、默认开启危险世界生成或向公开仓库提交用户私有资源。
- 把 `R0 完成` 表述为整个 MFQM 移植完成；不要跳过难点，也不要为了硬凑全量虚报成功。

**用户最希望得到的是：一个能够回答“原版到底有什么、新模组缺什么、哪些 AI 近似代码必须被替换、下一次修复哪个具体功能”的真实、可长期更新的工程，而不再是一堆相互独立、完成后无法追踪的阶段性报告。**
